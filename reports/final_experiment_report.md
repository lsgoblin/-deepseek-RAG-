# 基于 DeepSeek 的 RAG 提示词优化系统实验报告

## 1. 实验概述

### 1.1 实验背景

本实验围绕课程要求中的 RAG 系统实现展开，目标是在“文档处理 + 向量化 + 检索 + 生成”的基础上，完成一个可运行、可展示、可提交的课程项目。与通用问答不同，本项目选择了“AI 生图提示词优化”作为应用场景，以更清晰地展示 RAG 在创作辅助中的价值。

### 1.2 实验目标

本实验的目标包括：

- 构建本地知识库并支持多格式文档加载
- 基于向量检索完成相关提示词经验召回
- 调用 DeepSeek 生成优化后的提示词
- 支持 `LLM-only / Retrieval-only / RAG` 三模式对比
- 形成适合课程答辩与提交的完整交付材料

### 1.3 应用场景

本项目面向 AI 生图提示词优化，典型输入包括：

- 人物类提示词
- 场景类提示词
- 产品海报类提示词

系统输出优化后的提示词、来源文档和检索证据，用于帮助用户快速生成更高质量的图像提示词。

## 2. 系统设计

### 2.1 总体架构

系统采用标准 RAG 架构：

1. 本地知识库准备
2. 文档加载与文本切分
3. 文本向量化
4. 向量库存储
5. 用户输入提示词
6. 检索相似参考片段
7. 构造 Prompt
8. 调用 DeepSeek 生成结果
9. 返回优化提示词与来源证据

### 2.2 核心模块

- `loaders.py`：负责加载 `md / pdf / docx / xlsx`
- `splitter.py`：负责将文档切分为可索引片段
- `embedder.py`：负责调用 embedding 模型生成向量
- `vectordb.py`：负责 Chroma 向量库读写
- `retriever.py`：负责相似片段检索
- `prompt_builder.py`：负责构造 RAG Prompt
- `llm.py`：负责调用 DeepSeek API
- `prompt_optimizer.py`：负责提示词优化主逻辑
- `compare.py`：负责三模式对比实验
- `ui.py`：负责 CLI 交互入口
- `api_app.py`：负责 FastAPI Web 接口

### 2.3 技术选型

- 大模型：DeepSeek Chat
- 向量模型：`BAAI/bge-small-zh`
- 向量库：Chroma
- Web 后端：FastAPI
- 备用演示：Streamlit

选择原因：

- DeepSeek API 使用简单，适合课程原型项目
- `bge-small-zh` 适合中文语义检索
- Chroma 轻量、可持久化，适合本地实验
- FastAPI 部署与接口调试方便

## 5. 实验设计

### 5.1 实验目的

通过三种模式对比，验证 RAG 相对于纯大模型生成的优势，并分析其在提示词优化任务中的效果。

### 5.2 实验模式

#### 模式一：LLM-only

只调用大模型，不提供检索上下文。

特点：

- 输出直接
- 无来源依据
- 容易回到通用模板化生成

#### 模式二：Retrieval-only

只展示检索到的知识片段，不进行最终生成。

特点：

- 证据透明
- 可追溯性强
- 无法直接产出最终优化提示词

#### 模式三：RAG

先检索，再生成最终优化结果。

特点：

- 同时具备生成能力和证据能力
- 更适合课程实验展示
- 输出更容易与知识库内容保持一致

### 5.3 实验样例

本次实验使用三组标准输入：

#### 样例 1：人物类

- 原始提示词：`赛博朋克女战士站在雨夜街头`
- 平台：`即梦`
- 风格：`电影感，霓虹，高细节`
- 目标：`增强人物造型、场景氛围和镜头语言`

#### 样例 2：场景类

- 原始提示词：`清晨云海中的古风山寺`
- 平台：`Midjourney`
- 风格：`东方美学，空灵，层次丰富`
- 目标：`强化空间层次、光影和环境细节`

#### 样例 3：产品海报类

- 原始提示词：`一款高端香水的广告海报`
- 平台：`通用`
- 风格：`商业摄影，极简高级`
- 目标：`突出材质、品牌感和广告构图`

## 6. 实验结果

### 6.1 总体结果

项目已经生成完整的三模式对比实验结果，输出文件位于：

- `ai_deliverables/step-16-对比实验结果.json`
- `ai_deliverables/step-16-对比实验结果.md`

三组样例均成功完成：

- `LLM-only`
- `Retrieval-only`
- `RAG`

### 6.2 人物类样例结果分析

#### LLM-only

能够补充人物、雨夜街头、霓虹、镜头感等典型元素，结果较完整，但整体偏向常见“赛博朋克人物描述模板”，缺少与本地知识库的明确联系。

#### Retrieval-only

成功检索到 `jimeng_prompt_knowledge_base.md` 中与赛博朋克风格、镜头语言、光影效果相关的片段，说明检索链路有效。

#### RAG

在保留原始主题的基础上，进一步融入了知识库中的风格、光效、材质和构图元素，输出更具结构化特征，且可附带来源片段。

### 6.3 场景类样例结果分析

#### LLM-only

能够补充“云海、古寺、山峦、晨光”等常见东方场景元素，画面感较强。

#### Retrieval-only

成功检索到与光影、构图和层次相关的参考片段，说明系统可以从本地知识库中找出对场景强化有帮助的内容。

#### RAG

输出中能够明显体现光影层次、空间组织和镜头构图的增强，但也暴露出当前知识库并非专门针对“古风山寺”场景构建，因此个别参考特征与主题的贴合度不如产品类样例。

### 6.4 产品海报类样例结果分析

#### LLM-only

输出偏向标准商业摄影广告模板，能补充玻璃材质、灯光、构图和分辨率等信息。

#### Retrieval-only

成功检索到 `ai_image_prompts_synthesis.md` 中关于“商品图/海报 Prompt 模板”的规则，以及 `jimeng_prompt_knowledge_base.md` 中与光效和质感相关的结构化描述。

#### RAG

输出最完整，能够清楚补足：

- 材质：磨砂玻璃、金属、纹理、反光
- 构图：中央主体、低角度微距、留白
- 光线：侧顶光、轮廓光、反射光
- 约束：无文字、无水印

这一样例最能体现 RAG 在结构化提示词补全中的优势。

## 7. 实验结果对比分析

### 7.1 RAG 相比 LLM-only 的优势

- 输出更贴近本地知识库内容
- 更容易形成可解释的优化过程
- 能附带来源片段，便于课程答辩说明
- 对较短输入更容易补足结构化维度

### 7.2 Retrieval-only 的价值

虽然该模式不直接生成最终结果，但它在实验中具有重要作用：

- 证明系统确实进行了检索
- 可单独展示知识库命中效果
- 有利于分析知识库建设质量

### 7.3 三模式结论

从课程实验角度看：

- `LLM-only` 证明模型具备直接改写能力
- `Retrieval-only` 证明知识库与检索链路有效
- `RAG` 证明系统完成了“先检索、后生成”的完整闭环

因此，`RAG` 是本项目最核心、最适合最终展示的模式。
