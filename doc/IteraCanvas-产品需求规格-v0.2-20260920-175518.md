## 1. 产品定位

IteraCanvas 是一个面向图片创作者的跨平台创作诊断与迭代助手。

它不负责替用户生成图片，而是帮助用户：

1. 从模糊描述中逐步形成可验证的创作需求。
2. 根据用户在外部平台获得的真实生成结果进行诊断。
3. 找出结果与创作目标之间的差距。
4. 输出平台适配或通用的修改补丁。
5. 记录多轮结果，帮助用户以更少生成轮次达到可接受结果。

产品核心指标是：用户达到可接受结果所需的外部生成轮次。

## 2. 产品边界

### 2.1 已确认范围

- 支持诊断所有类型的图片，不限定特定生图平台。
- 用户在外部平台完成图片生成。
- 用户将生成结果上传到 IteraCanvas。
- 文本和图片分析均通过外部多模态 API 完成。
- 允许用户不填写平台、模型、提示词或参数。
- 已知平台与模型时，系统可输出平台适配建议；未知时输出通用建议。
- 用户是诊断结论和最终结果的最终裁决者。
- 保存任务、图片、规格、诊断、补丁和迭代历史。
- 用户可以永久删除任务及其本地数据。

### 2.2 当前明确不做

- 不内置图片生成 API。
- 不替用户自动选择“最佳图片”。
- 不在 Skills 展厅中执行 Skill。
- Demo 阶段不实现多人协作。
- Demo 阶段不实现在线安装、GitHub 自动同步和 Skill 下载。
- Demo 阶段不要求接入 Codex CLI、MCP 或 Plugin。

## 3. 产品模块

### 3.1 跨平台图片诊断助手

负责创作规格整理、图片上传、逐项诊断、诊断复核、修改补丁、多轮比较、任务分支和结果接受。

### 3.2 图片 Skills 展厅

负责在 Web 中展示本地仓库中的图片类 Skills，例如科研图片风格 Skill 等。

当前仅确定两个模块可以共享同一个后端服务；共享技术底座不等于形成统一产品闭环。两个模块是否必须在同一个 Demo 中交付、如何互相导流，以及是否共享同一组成功指标，均属于第 17.5 节的基线阻断决策。

## 4. 核心用户流程

```text
创建创作任务
→ 用户用自由文本描述创作目标，可上传参考图
→ AI 一次性提出当前缺失的问题
→ 用户回答或跳过问题
→ 系统形成可继续修改的创作规格
→ 用户确认当前规格
→ 用户在外部平台生成图片
→ 用户上传一张或多张结果图片
→ 系统逐项诊断
→ 用户确认或纠正诊断
→ 用户选择一个或多个问题进行修复
→ 系统输出修改补丁
→ 用户在外部平台完成下一轮生成
→ 用户上传下一轮结果
→ 系统仅展示本轮与上一轮的差异
→ 重复迭代，直到用户接受结果
```

> 流程图中的“下一轮”暂指用户完成一次新的外部生成行为，不以单次上传动作作为最终定义。分批上传、重复上传和一次生成返回多图的归属规则见第 17.3 节，确认前不得据此冻结数据结构。

## 5. 创作规格

### 5.1 已确认原则

- 用户通过自由文本描述需求，不要求填写固定大表单。
- 用户可能并不完全了解自己的需求。
- AI 负责从用户描述和参考图中提取创作规格，并对关键缺失项进行追问。
- 追问采用一次性集中提问方式。
- 用户可以跳过问题。
- 创作规格允许不完整，并可以在后续迭代中继续修改。
- 小幅变化保留在原任务中。
- 目的、主体、比例、核心硬约束或评价标准发生重大变化时，应创建任务分支。
- 新分支默认继承原任务的参考图、提示词和创作规格。

### 5.2 建议结构（待确认）

创作规格由“任务上下文”和“可验证要求列表”组成，而不是要求所有固定字段都有值。

#### 任务上下文

- 目标用途
- 投放平台或使用场景
- 目标受众
- 主体、场景和动作
- 风格、构图、色彩和光线
- 输出比例和尺寸
- 图片中的准确文字及可读性要求
- 排除项
- 参考图片及参考用途

#### 可验证要求 `criteria[]`

每条要求建议包含：

| 字段 | 含义 |
| --- | --- |
| `id` | 要求唯一标识 |
| `category` | 主体、构图、风格、文字、颜色、用途等分类 |
| `statement` | 可直接判断的要求内容 |
| `importance` | 硬约束、软偏好或未决定 |
| `source` | 用户明确、AI 推断或系统建议 |
| `status` | 已确认、待确认或未知 |
| `verification_mode` | 视觉、提示词、参数或用户判断 |

只有已确认的硬约束可以被系统判定为明确通过或未通过。

### 5.3 规格版本（待确认）

当前建议将创作规格设计为不可变版本：每次修改生成新的 `spec_version_id`，图片提交、诊断和补丁必须绑定其产生时使用的规格版本。历史结果不得被新规格自动重新解释。重大变化除生成新版本外，还应创建任务分支。最终版本规则及迁移方式见第 17.4 节。

## 6. 参考图片

### 6.1 已确认规则

- 支持上传参考图片。
- 参考图片可以用于表达风格、构图、角色或产品、颜色等要求。
- 如果用户没有说明参考图用途，系统自动判断并请求用户确认。
- 系统的自动判断不能被当成用户已经确认的事实。

## 7. 图片上传与多结果处理

### 7.1 当前工作假设（待确认）

- 一次外部生成行为可以返回一张或多张图片，并暂记为一个生成轮次。
- 多图片场景只展示差异，不进行自动排名，也不替用户选择最佳结果。
- 用户可以选择一张图片继续下一轮，也可以根据多张结果自行判断。
- 提示词和生成参数不是强制输入，但系统应推荐用户提供。

上传动作暂定义为“图片提交”，不自动等同于“生成轮次”。分批上传可追加到同一轮；重复文件不应自动创建新轮次；具体识别和人工纠正机制见第 17.3 节。

### 7.2 信息完整度对诊断的影响

- 仅有图片：提供视觉诊断和通用修改建议。
- 图片和提示词：可以输出更精确的提示词修改补丁。
- 图片、提示词和参数：可以同时输出提示词和参数修改建议。
- 信息缺失时，系统应明确说明诊断依据和不确定性。

## 8. 诊断结果

### 8.1 已确认诊断范围

- 明确创作要求的满足情况。
- 构图、色彩、光线和视觉层级等审美问题。
- 根据图片用途判断商业表现。
- 与参考图片的对齐情况。
- 与上一轮结果相比的改善和退步。

审美诊断属于建议，不应自动等同于创作规格失败。

### 8.2 建议结构（待确认）

每条诊断结果与一个创作要求或一个独立观察项关联，并包含：

- 通过、未通过、不确定或不适用。
- 图片中的具体证据及位置。
- 问题严重程度。
- 模型置信度。
- 可能原因。
- 是否违反已确认硬约束。
- 用户确认、纠正或否定的结果。

AI 原始诊断和用户纠正结果分别保存，不相互覆盖。

## 9. 修改补丁

### 9.1 当前工作假设（待确认）

- 用户自行选择需要修复的问题。
- 一轮可以同时选择多个问题。
- 诊断和修改界面默认突出展示差异。
- 当多个修改可能冲突，或一次修改多个变量会降低因果判断能力时，系统应提示用户。

“只展示差异”仅是界面展示原则，不代表系统只保存差异。为保证结果可追溯且可直接使用，系统应同时保存基准快照和结构化差异，并提供合并后的完整提示词与完整参数供用户复制。该建议需按第 17.6 节完成评审后才能成为基线规则。

### 9.2 建议结构（待确认）

- 关联的问题 ID。
- 提示词增加、删除或替换内容。
- 参数原值与建议值。
- 局部重绘、重新构图、重新上传参考图等操作建议。
- 下一轮需要保持不变的正确部分。
- 多个修改之间的冲突。
- 修改可能带来的副作用。
- 适用平台和模型；未知时标记为通用补丁。

## 10. 任务、轮次与分支

### 10.1 当前工作假设（待确认）

- 保存完整任务历史。
- 一次新的外部生成行为形成一个生成轮次；上传只是向该轮提交结果图片。
- 用户可以在任意轮次修改创作规格。
- 重大规格变化创建分支任务。
- 分支默认继承原任务信息。
- 用户明确接受结果后任务完成。

系统无法可靠自动识别外部生成行为时，应让用户选择“追加到当前轮”或“创建新一轮”。分批上传、重复上传、一轮多图以及纠错规则仍需按第 17.3 节确认。

### 10.2 建议状态模型（待确认）

任务状态：

```text
草稿 → 进行中 → 已接受
```

轮次状态：

```text
等待图片 → 诊断中 → 等待用户复核 → 补丁已生成 → 已结束
```

外部诊断失败时保留当前轮次，允许用户重试，不推进任务状态。

## 11. 本地数据与隐私

### 11.1 已确认规则

- Demo 为本地运行、本人可见的单用户版本。
- 任务数据和图片保存在本地。
- 外部 API 密钥保存在本地 `.env` 文件中。
- 图片发送到第三方模型前必须向用户说明，并获得明确授权。
- 用户可以永久删除一个任务的全部本地数据。
- “永久删除”仅指 IteraCanvas 可控制的本地数据；不得暗示第三方供应商会同步删除其已接收的数据。

### 11.2 建议实现规则（待确认）

- SQLite 保存结构化数据。
- 本地文件目录保存原图和处理后的副本。
- 使用任务 ID 和轮次 ID 隔离文件目录。
- 发送外部 API 前生成去除 EXIF 信息的副本，原图保持不变。
- 删除任务时级联删除数据库记录、原图和中间文件。
- 支持 PNG、JPEG 和 WebP，具体文件大小和尺寸限制在选定模型后确定。
- 授权记录包含供应商、模型、时间和授权范围。
- 授权界面应披露第三方的用途、保留期限和删除能力；若供应商未提供远程删除能力，必须明确告知用户。
- 用户拒绝或撤回授权后，系统不得继续发起新的外部调用，但仍允许查看、导出或删除已保存的本地数据。

## 12. 外部多模态 API

### 12.1 已确认规则

- 图片与文本分析均通过外部 API 完成。
- 具体供应商和模型尚未确定。
- Demo 不需要同时支持多个供应商。
- 供应商未确定前，可以使用模拟结果开发核心业务流程。

### 12.2 建议失败处理（待确认）

- 模型输出必须通过结构化字段校验。
- 超时、限流和服务端错误只进行有限次数重试。
- 结构化输出无效时，诊断标记失败并允许重试。
- 失败不能生成半完整诊断，也不能破坏已有任务数据。
- 更换图片接收方或供应商时重新获得用户授权。

## 13. Skills 展厅

### 13.1 已确认规则

- Skills 在 Demo 阶段存放于本地仓库。
- Skills 由管理员手动发布。
- 发布前需要进行校验。
- Web 展示 Skill 的说明、案例和完整文本。
- 用户可以复制 Skill 文本并手动粘贴使用。
- Web 不执行 Skill。
- Demo 不提供下载、GitHub 自动同步和在线安装。
- 首批 Skill 清单已确定为第 13.3 节所列 8 项；进入本地采集区不等于取得公开发布或商业使用授权。

### 13.2 建议校验规则（待确认）

禁止发布的错误：

- 缺少 `SKILL.md`。
- 元数据结构无法解析。
- Skill 名称重复。
- 引用文件不存在。
- 路径越界或引用本地仓库之外的文件。

可提示的完整性问题：

- 缺少示例。
- 缺少效果说明。
- 缺少安装或来源元数据。

完整性问题是否允许管理员强制发布仍待确认。

上述“禁止发布”规则适用于声称可直接使用或可安装的完整 Skill 包。本轮按产品要求采集的是 `content_only` 核心正文快照，只用于本机研究、授权评估和展厅数据结构开发；快照可以缺少正文引用的 `references/`、`scripts/` 或 `assets/`，但此时必须标记为“非完整包”，不得进入可发布状态，也不得向用户提供安装入口。

### 13.4 本地采集与发布状态

- 本地采集清单以 `data/skills-showcase/manifest.json` 为唯一事实来源，至少记录展厅 ID、frontmatter 名称、来源仓库、来源路径、提交哈希、正文哈希、许可类型和发布状态。
- 第三方核心正文和上游许可证副本默认由 `.gitignore` 排除，避免把本地下载误提交为产品分发内容；清单和本说明可以进入版本控制。

- 从本地采集区复制正文到发布库属于独立发布动作，必须记录操作者、时间、目标版本、授权依据和校验结果。

## 14. Codex 集成规划

### 14.1 已确认方向

- Codex CLI 是附加入口，不是 Demo 主界面。
- 最终可以将核心工作流封装为 Codex Skill。
- Web 与 Codex Skill 共享同一个后端服务。
- 后续可以通过 MCP 暴露创建任务、提交轮次、诊断、生成补丁、比较和接受结果等操作。
- 更长期可以封装为 Plugin。

## 15. Demo 对比实验

### 15.1 已确认目标

- 对比人工修改流程与 IteraCanvas 辅助流程。
- 先使用固定、可重复的创作案例。
- 后续条件允许时再加入真实创作者。
- 核心指标是达到用户可接受结果所需的生成轮次。

### 15.2 建议计量规则（待确认）

- 计量候选规则为：一次外部平台生成请求计为一轮，无论该次返回一张还是多张候选图；上传次数不计为轮次。
- 只有用户明确点击“接受结果”才算任务完成。
- 两组实验使用相同需求、参考图、模型版本和初始参数。
- 辅助指标包括耗时、硬约束通过率、修改建议采用率和问题回退数量。
- 固定案例数量、案例类型、最大轮次、单任务成本上限、超时规则、实验顺序和真实参与人数尚未确定。
- 为降低学习效应和顺序偏差，人工流程与辅助流程的先后顺序应随机化或采用平衡顺序；同一参与者是否同时体验两组也需在实验前固定。

## 16. 非功能要求

- 本地 Demo 中的任务和图片默认仅本人可见。
- 模型调用失败不能造成已保存历史丢失。
- 所有 AI 推断应标注来源和置信度。
- 系统不得把未确认的 AI 推断表述为用户要求。
- 用户纠正诊断后，后续补丁使用纠正后的结论。
- 关键状态变化和外部 API 调用应具有可追踪记录。

### 17.1 P0-01 文档基线状态不成立

**现状**：核心业务规则、数据结构、模型供应商和实验标准均未冻结，将当前文档称为“需求基线”会造成研发和测试把工作假设误当作确定要求。

**建议决策**：当前版本维持“需求草案（非需求基线）”。第 17 章全部 P0 项关闭、核心数据结构通过评审且验收阈值补齐后，再发布新的基线版本；不得直接覆盖本草案。

**关闭标准**：

- 为每个 P0 项记录结论、决策日期、决策人和受影响章节。
- 给出本期范围、明确不做、外部依赖和变更控制方式。
- 发布新版本号并保留本草案，评审人签字或通过等价的电子审批。

### 17.2 P0-02 新产品与现有 RAG 系统关系不明确

**现状**：仓库现有能力是提示词 RAG 优化、知识库检索和三模式实验，新文档描述的是跨平台图片诊断与迭代。两者的用户输入、核心流程和验证指标不同，原课程交付要求是否仍为硬约束也未确认。

**建议决策**：在课程要求确认前采用“双轨保留、接口复用”的低风险方案：保留现有 RAG 演示和实验链路，不把它默认等同于新产品；评估其检索能力能否作为诊断补丁生成的可选能力。是否废弃旧入口必须在课程约束确认后另行决定。

**必须回答**：

1. 原课程对 RAG、知识库、三模式实验和交付文件有哪些不可删除的硬约束？
2. 现有 `/api/optimize`、CLI、知识库和实验脚本分别保留、改造、复用还是废弃？
3. RAG 若进入新流程，服务的是“规格形成”“诊断”还是“补丁生成”，其失败是否阻断主流程？
4. 新旧入口是否共享数据、接口和成功指标，如何避免用户误以为是同一功能？

**关闭标准**：形成逐项能力处置矩阵，至少包含当前能力、目标能力、处置方式、迁移时间、课程影响和回退方案。

### 17.3 P0-03 “生成轮次”的定义存在冲突

**现状**：旧表述同时把上传动作和外部生成行为视为新轮次，无法一致处理分批上传、重复上传和一次生成多图，也会直接扭曲核心指标。

**建议术语**：

- **生成轮次 `generation_round`**：用户在外部平台发起的一次生成请求。
- **图片提交 `submission`**：用户向某个生成轮次上传一次或多次文件的动作。
- **候选图 `candidate`**：一次生成请求返回的单张图片。

**建议规则**：一轮可含多张候选图和多次图片提交；分批上传默认追加到用户指定的同一轮；同一文件重复上传不自动新增候选图或轮次；只有用户声明完成了新的外部生成，或提供新的外部生成标识时，才创建下一轮。系统判断不确定时必须让用户选择“追加到当前轮”或“创建新一轮”，并允许纠正归属。

**关闭标准**：统一第 4、7、10、15 章术语，数据模型能表达一轮多图和多次提交，并通过分批上传、重复上传、跨轮误传和轮次归属纠正四类测试。

### 17.4 P0-04 创作规格缺少版本管理规则

**现状**：用户可在任意时点修改规格，但图片、诊断和补丁未绑定规格版本，历史结果可能被新规格错误解释。

**建议规则**：规格采用不可变版本。每次保存修改均创建新的 `spec_version_id`；每个生成轮次绑定生成时采用的规格版本；每条诊断绑定被诊断图片及其规格版本；每个补丁同时绑定来源规格版本和目标规格版本。新版本不得覆盖或自动改写历史诊断。重大变化创建分支，轻微变化留在原任务但仍产生新版本。

**关闭标准**：确定版本创建时机、草稿是否编号、回退方式、分支继承方式和旧数据迁移规则；界面始终能显示“当前查看结果依据的规格版本”。

### 17.5 P0-05 诊断助手与 Skills 展厅缺少统一产品闭环

**现状**：诊断助手以减少外部生成轮次为目标；Skills 展厅以发现、阅读和复制 Skill 为目标。二者的目标用户、路径和成功指标不同，共用后端不足以证明必须在一个 Demo 中共同交付。

**建议决策**：将诊断助手设为主 Demo，Skills 展厅作为独立次级入口和可裁剪交付项。只有当展厅能够明确支持诊断流程中的一个节点，例如把 Skill 作为创作方法参考并回填到规格或补丁，才定义跨模块闭环；Demo 阶段不强行把“浏览 Skill”计入诊断成功。

**必须回答**：两个模块共同服务的用户任务是什么；用户从哪个模块进入另一个模块；跨模块传递什么数据；若移除展厅，诊断助手的核心价值是否受损；若必须共同交付，是产品原因还是课程展示要求。

**关闭标准**：输出一张模块关系图，分别定义入口、退出、核心动作和成功指标，并明确“同一 Demo”“同一仓库”与“同一产品闭环”三者的边界。

### 17.6 P0-06 “只展示差异”的规则不完整

**现状**：“只展示差异”没有区分界面展示与持久化策略，也没有说明用户如何获得可直接粘贴到外部平台的完整提示词和参数。

**建议规则**：界面默认突出显示新增、删除和替换项；系统同时保存输入基准快照、结构化差异和合并后的结果快照。每个补丁必须关联基准提示词、基准参数和规格版本，并提供“一键复制完整提示词”“复制完整参数”和“查看差异”。合并冲突必须显式提示，不得静默覆盖用户内容。

**关闭标准**：明确快照与差异的唯一事实来源、合并顺序、空值处理、参数删除语义、冲突处理和历史重放方式，并通过多补丁合并与旧版本回放测试。

### 17.7 P0-07 用户确认、跳过问题和 AI 推断之间的规则不明确

**现状**：尚未定义用户确认规格是否会连带确认 AI 推断项、跳过项能否参与诊断，以及用户纠正诊断后如何影响补丁和后续轮次。

**建议规则**：

- “确认规格”只确认界面中明确列出且由用户勾选或编辑确认的内容，不自动把所有 AI 推断转为用户事实。
- AI 推断保持 `待确认` 和 `AI 推断` 来源；可作为明确标注的软建议，但不得用于硬约束通过/失败判断。
- 用户跳过的问题记为 `未知/已跳过`，不参与通过率分母，不得造成任务失败；如参与建议生成，必须说明其假设性质。
- 用户可对诊断执行确认、纠正、不适用或无法判断；后续补丁和比较使用用户纠正后的有效结论，同时保留 AI 原始结果和审计记录。

**关闭标准**：产出 `source × status × importance` 状态转换表，覆盖批量确认、取消确认、跳过后补填、纠正诊断和撤销纠正。

### 17.8 P0-08 隐私、授权与删除边界不完整

**现状**：本地永久删除不代表第三方同步删除。授权范围、授权失效、拒绝授权、调用日志清理以及供应商数据保留策略均未完整定义。

**建议规则**：授权至少绑定任务、供应商、模型、数据类型、用途、时间和政策版本；更换供应商、用途扩大、政策实质变化或授权撤回后再次调用时必须重新授权。拒绝授权时禁止上传到第三方，但允许用户继续使用不依赖外部调用的本地功能。删除任务时删除本地结构化数据、原图、衍生图、缓存和可关联调用日志；第三方删除仅在供应商提供能力时发起，并分别展示本地删除结果与第三方处理状态。

**关闭标准**：选定供应商后记录其训练使用、保留期限、区域、日志、删除接口和失败处理政策；授权文案不得承诺产品无法控制的第三方删除结果。

### 17.9 P0-09 核心指标和对比实验缺乏可靠计量方法

**现状**：“可接受结果”依赖主观点击，一轮候选图数量不受控也可能提高偶然命中概率；最大轮次、成本、耗时和实验顺序尚未固定。

**建议计量框架**：

- 主指标：在固定外部生成请求定义下，达到预先声明的任务验收门槛所需生成轮次。
- 完成条件：用户点击接受，且预先定义的硬约束通过；两者分开记录，不以单一主观点击替代。
- 控制变量：相同案例、模型及版本、初始提示词/参数、每轮候选图数量、最大轮次、单任务预算和超时规则。
- 辅助指标：总耗时、模型与平台成本、硬约束通过率、建议采用率、回退数和失败调用数。
- 顺序控制：随机分组或平衡两种流程的先后次序；正式实验前固定案例和分析方法，不根据结果临时改口径。

**关闭标准**：实验方案明确样本量、案例分层、每轮候选图上限、最大轮次、预算、计时起止点、退出规则、顺序分配和异常数据处理，并用至少一轮预实验验证记录方式可执行。

### 17.10 P0-10 缺少可直接测试的验收标准

**现状**：图片限制、处理时限、失败重试、异常流程、分支、删除、规格版本和诊断纠正均缺少可验证的输入、动作和预期结果。

**最低验收用例集**：

| 用例 ID | 场景 | 最低可验证结果 |
| --- | --- | --- |
| AC-IMG-01 | 上传受支持和不受支持的图片 | 合法文件成功入库；非法格式、超大小或超尺寸文件被明确拒绝，且不创建错误轮次 |
| AC-RND-01 | 一轮多图、分批上传和重复上传 | 图片归属同一指定轮次；重复文件按既定规则处理；轮次计数不因上传次数增加 |
| AC-API-01 | 模型超时、限流、服务错误或结构无效 | 在明确时限和重试次数内结束；失败可重试、无半成品、已有历史不受损 |
| AC-AUTH-01 | 拒绝、撤回或需要重新授权 | 不发生未授权外部调用；本地可用功能仍可访问；重新授权触发条件正确 |
| AC-SPEC-01 | 修改规格后查看旧轮次 | 新建规格版本；旧图片、诊断和补丁仍绑定原版本，不被新规格重写 |
| AC-BRANCH-01 | 重大规格变化并创建分支 | 分支继承规则正确，原任务不变，父子关系可追溯 |
| AC-DIAG-01 | 用户纠正、否定或撤销诊断 | 原始诊断保留；有效结论和后续补丁按用户最新决定更新 |
| AC-PATCH-01 | 生成并应用一个或多个差异补丁 | 可查看差异并复制合并后的完整提示词和参数；冲突不会被静默覆盖 |
| AC-DEL-01 | 删除含多轮数据的任务 | 所有受控本地数据和关联日志按规则删除；第三方状态单独说明且不误报 |
| AC-RECOVER-01 | 处理中刷新、关闭或重复提交 | 按既定幂等规则恢复，不重复创建轮次、诊断或计费调用 |

**关闭标准**：为所有用例补齐确定数值，包括支持格式、单文件大小、图片尺寸、每轮图片数、任务容量、处理时限、重试次数和最大轮次；使用 Given/When/Then 编写并由测试人员在无口头解释的情况下独立执行通过。

### 17.11 其他非阻断待确认项

以下问题仍需确认，但不替代上述十项 P0 决策：

1. Demo 主界面继续使用 FastAPI 加 HTML，还是使用 Streamlit。
2. 创作规格 `criteria[]` 是否确定为诊断和补丁的核心关联方式。
3. Demo 首个多模态 API 的具体供应商和模型版本。
4. Skills 完整性校验失败后是否允许管理员强制发布。
5. 首批 8 个图片 Skills 的公开发布授权复核（清单与本地正文采集已完成）。
6. 重大规格变化由系统提示后用户确认，还是完全由用户主动决定。

## 18. 当前开发顺序建议

1. 先关闭 P0-01、P0-02 和 P0-05，明确基线、课程约束和本期模块范围。
2. 关闭 P0-03、P0-04、P0-06 和 P0-07，冻结核心术语、状态转换及数据结构。
3. 关闭 P0-08 并确定首个多模态供应商，再实现真实外部调用；此前使用模拟结果开发。
4. 实现任务、规格版本、生成轮次、图片提交、诊断、补丁、分支和本地存储。
5. 使用模拟模型跑通完整诊断迭代闭环，并执行 P0-10 的非供应商相关用例。
6. 接入一个外部多模态 API，补齐图片限制、时限、重试和授权测试。
7. 完成诊断 Web 界面；根据 P0-05 结论决定是否在本期交付 Skills 展厅。
8. 关闭 P0-09，完成预实验后再开展正式对比实验。
9. 核心流程稳定后，再增加 Codex Skill、MCP、协作和多供应商能力。
