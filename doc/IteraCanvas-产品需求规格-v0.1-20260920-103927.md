# IteraCanvas（迭绘）产品需求规格

## 文档信息

- 文档版本：v0.1
- 生成时间：2026-09-20 10:39:27（Asia/Shanghai）
- 文档状态：需求基线，待继续确认
- 产品名称：IteraCanvas（迭绘）
- 当前阶段：本地单用户 Demo 设计阶段

> 本文档区分“已确认需求”“建议设计”和“未决问题”。建议设计尚未经过产品确认，不能直接视为最终业务规则。

## 1. 产品定位

IteraCanvas 是一个面向图片创作者的跨平台创作诊断与迭代助手。

它不负责替用户生成图片，而是帮助用户：

1. 从模糊描述中逐步形成可验证的创作需求。
2. 根据用户在外部平台获得的真实生成结果进行诊断。
3. 找出结果与创作目标之间的差距。
4. 输出平台适配或通用的修改补丁。
5. 记录多轮结果，帮助用户以更少生成轮次达到可接受结果。

产品核心指标是：用户达到可接受结果所需的外部生成轮次。

## 2. 产品边界

### 2.1 已确认范围

- 支持诊断所有类型的图片，不限定特定生图平台。
- 用户在外部平台完成图片生成。
- 用户将生成结果上传到 IteraCanvas。
- 文本和图片分析均通过外部多模态 API 完成。
- 允许用户不填写平台、模型、提示词或参数。
- 已知平台与模型时，系统可输出平台适配建议；未知时输出通用建议。
- 用户是诊断结论和最终结果的最终裁决者。
- 保存任务、图片、规格、诊断、补丁和迭代历史。
- 用户可以永久删除任务及其本地数据。

### 2.2 当前明确不做

- 不内置图片生成 API。
- 不替用户自动选择“最佳图片”。
- 不在 Skills 展厅中执行 Skill。
- Demo 阶段不实现多人协作。
- Demo 阶段不实现在线安装、GitHub 自动同步和 Skill 下载。
- Demo 阶段不要求接入 Codex CLI、MCP 或 Plugin。

## 3. 产品模块

### 3.1 跨平台图片诊断助手

负责创作规格整理、图片上传、逐项诊断、诊断复核、修改补丁、多轮比较、任务分支和结果接受。

### 3.2 图片 Skills 展厅

负责在 Web 中展示本地仓库中的图片类 Skills，例如科研图片风格 Skill 等。

两个模块共享同一个后端服务。

## 4. 核心用户流程

```text
创建创作任务
→ 用户用自由文本描述创作目标，可上传参考图
→ AI 一次性提出当前缺失的问题
→ 用户回答或跳过问题
→ 系统形成可继续修改的创作规格
→ 用户确认当前规格
→ 用户在外部平台生成图片
→ 用户上传一张或多张结果图片
→ 系统逐项诊断
→ 用户确认或纠正诊断
→ 用户选择一个或多个问题进行修复
→ 系统输出修改补丁
→ 用户在外部平台完成下一轮生成
→ 用户上传下一轮结果
→ 系统仅展示本轮与上一轮的差异
→ 重复迭代，直到用户接受结果
```

## 5. 创作规格

### 5.1 已确认原则

- 用户通过自由文本描述需求，不要求填写固定大表单。
- 用户可能并不完全了解自己的需求。
- AI 负责从用户描述和参考图中提取创作规格，并对关键缺失项进行追问。
- 追问采用一次性集中提问方式。
- 用户可以跳过问题。
- 创作规格允许不完整，并可以在后续迭代中继续修改。
- 小幅变化保留在原任务中。
- 目的、主体、比例、核心硬约束或评价标准发生重大变化时，应创建任务分支。
- 新分支默认继承原任务的参考图、提示词和创作规格。

### 5.2 建议结构（待确认）

创作规格由“任务上下文”和“可验证要求列表”组成，而不是要求所有固定字段都有值。

#### 任务上下文

- 目标用途
- 投放平台或使用场景
- 目标受众
- 主体、场景和动作
- 风格、构图、色彩和光线
- 输出比例和尺寸
- 图片中的准确文字及可读性要求
- 排除项
- 参考图片及参考用途

#### 可验证要求 `criteria[]`

每条要求建议包含：

| 字段 | 含义 |
| --- | --- |
| `id` | 要求唯一标识 |
| `category` | 主体、构图、风格、文字、颜色、用途等分类 |
| `statement` | 可直接判断的要求内容 |
| `importance` | 硬约束、软偏好或未决定 |
| `source` | 用户明确、AI 推断或系统建议 |
| `status` | 已确认、待确认或未知 |
| `verification_mode` | 视觉、提示词、参数或用户判断 |

只有已确认的硬约束可以被系统判定为明确通过或未通过。

## 6. 参考图片

### 6.1 已确认规则

- 支持上传参考图片。
- 参考图片可以用于表达风格、构图、角色或产品、颜色等要求。
- 如果用户没有说明参考图用途，系统自动判断并请求用户确认。
- 系统的自动判断不能被当成用户已经确认的事实。

## 7. 图片上传与多结果处理

### 7.1 已确认规则

- 单轮允许上传一张或多张图片。
- 多图片场景只展示差异，不进行自动排名，也不替用户选择最佳结果。
- 用户可以选择一张图片继续下一轮，也可以根据多张结果自行判断。
- 提示词和生成参数不是强制输入，但系统应推荐用户提供。

### 7.2 信息完整度对诊断的影响

- 仅有图片：提供视觉诊断和通用修改建议。
- 图片和提示词：可以输出更精确的提示词修改补丁。
- 图片、提示词和参数：可以同时输出提示词和参数修改建议。
- 信息缺失时，系统应明确说明诊断依据和不确定性。

## 8. 诊断结果

### 8.1 已确认诊断范围

- 明确创作要求的满足情况。
- 构图、色彩、光线和视觉层级等审美问题。
- 根据图片用途判断商业表现。
- 与参考图片的对齐情况。
- 与上一轮结果相比的改善和退步。

审美诊断属于建议，不应自动等同于创作规格失败。

### 8.2 建议结构（待确认）

每条诊断结果与一个创作要求或一个独立观察项关联，并包含：

- 通过、未通过、不确定或不适用。
- 图片中的具体证据及位置。
- 问题严重程度。
- 模型置信度。
- 可能原因。
- 是否违反已确认硬约束。
- 用户确认、纠正或否定的结果。

AI 原始诊断和用户纠正结果分别保存，不相互覆盖。

## 9. 修改补丁

### 9.1 已确认规则

- 用户自行选择需要修复的问题。
- 一轮可以同时选择多个问题。
- 系统不直接输出一份替换全部内容的新方案，而是只展示差异。
- 当多个修改可能冲突，或一次修改多个变量会降低因果判断能力时，系统应提示用户。

### 9.2 建议结构（待确认）

- 关联的问题 ID。
- 提示词增加、删除或替换内容。
- 参数原值与建议值。
- 局部重绘、重新构图、重新上传参考图等操作建议。
- 下一轮需要保持不变的正确部分。
- 多个修改之间的冲突。
- 修改可能带来的副作用。
- 适用平台和模型；未知时标记为通用补丁。

## 10. 任务、轮次与分支

### 10.1 已确认规则

- 保存完整任务历史。
- 每次上传外部生成结果形成一个新轮次。
- 用户可以在任意轮次修改创作规格。
- 重大规格变化创建分支任务。
- 分支默认继承原任务信息。
- 用户明确接受结果后任务完成。

### 10.2 建议状态模型（待确认）

任务状态：

```text
草稿 → 进行中 → 已接受
```

轮次状态：

```text
等待图片 → 诊断中 → 等待用户复核 → 补丁已生成 → 已结束
```

外部诊断失败时保留当前轮次，允许用户重试，不推进任务状态。

## 11. 本地数据与隐私

### 11.1 已确认规则

- Demo 为本地运行、本人可见的单用户版本。
- 任务数据和图片保存在本地。
- 外部 API 密钥保存在本地 `.env` 文件中。
- 图片发送到第三方模型前必须向用户说明，并获得明确授权。
- 用户可以永久删除一个任务的全部本地数据。

### 11.2 建议实现规则（待确认）

- SQLite 保存结构化数据。
- 本地文件目录保存原图和处理后的副本。
- 使用任务 ID 和轮次 ID 隔离文件目录。
- 发送外部 API 前生成去除 EXIF 信息的副本，原图保持不变。
- 删除任务时级联删除数据库记录、原图和中间文件。
- 支持 PNG、JPEG 和 WebP，具体文件大小和尺寸限制在选定模型后确定。
- 授权记录包含供应商、模型、时间和授权范围。

## 12. 外部多模态 API

### 12.1 已确认规则

- 图片与文本分析均通过外部 API 完成。
- 具体供应商和模型尚未确定。
- Demo 不需要同时支持多个供应商。
- 供应商未确定前，可以使用模拟结果开发核心业务流程。

### 12.2 建议失败处理（待确认）

- 模型输出必须通过结构化字段校验。
- 超时、限流和服务端错误只进行有限次数重试。
- 结构化输出无效时，诊断标记失败并允许重试。
- 失败不能生成半完整诊断，也不能破坏已有任务数据。
- 更换图片接收方或供应商时重新获得用户授权。

## 13. Skills 展厅

### 13.1 已确认规则

- Skills 在 Demo 阶段存放于本地仓库。
- Skills 由管理员手动发布。
- 发布前需要进行校验。
- Web 展示 Skill 的说明、案例和完整文本。
- 用户可以复制 Skill 文本并手动粘贴使用。
- Web 不执行 Skill。
- Demo 不提供下载、GitHub 自动同步和在线安装。
- 初始 Skill 清单由产品方后续寻找和确定。

### 13.2 建议校验规则（待确认）

禁止发布的错误：

- 缺少 `SKILL.md`。
- 元数据结构无法解析。
- Skill 名称重复。
- 引用文件不存在。
- 路径越界或引用本地仓库之外的文件。

可提示的完整性问题：

- 缺少示例。
- 缺少效果说明。
- 缺少安装或来源元数据。

完整性问题是否允许管理员强制发布仍待确认。

## 14. Codex 集成规划

### 14.1 已确认方向

- Codex CLI 是附加入口，不是 Demo 主界面。
- 最终可以将核心工作流封装为 Codex Skill。
- Web 与 Codex Skill 共享同一个后端服务。
- 后续可以通过 MCP 暴露创建任务、提交轮次、诊断、生成补丁、比较和接受结果等操作。
- 更长期可以封装为 Plugin。

## 15. Demo 对比实验

### 15.1 已确认目标

- 对比人工修改流程与 IteraCanvas 辅助流程。
- 先使用固定、可重复的创作案例。
- 后续条件允许时再加入真实创作者。
- 核心指标是达到用户可接受结果所需的生成轮次。

### 15.2 建议计量规则（待确认）

- 一次外部平台生成行为计为一轮，无论该次返回一张还是多张候选图。
- 只有用户明确点击“接受结果”才算任务完成。
- 两组实验使用相同需求、参考图、模型版本和初始参数。
- 辅助指标包括耗时、硬约束通过率、修改建议采用率和问题回退数量。
- 固定案例数量、案例类型、最大轮次和真实参与人数尚未确定。

## 16. 非功能要求

- 本地 Demo 中的任务和图片默认仅本人可见。
- 模型调用失败不能造成已保存历史丢失。
- 所有 AI 推断应标注来源和置信度。
- 系统不得把未确认的 AI 推断表述为用户要求。
- 用户纠正诊断后，后续补丁使用纠正后的结论。
- 关键状态变化和外部 API 调用应具有可追踪记录。

## 17. 当前未决问题

按对数据结构和产品行为的影响排序：

1. 用户跳过追问后，AI 推断项是否可以作为软偏好参与诊断和补丁生成，还是只能显示为观察建议。
2. Demo 使用的首个多模态 API 供应商、模型版本、图片限制和费用上限。
3. Demo 主界面继续使用 FastAPI 加 HTML，还是使用 Streamlit。
4. 创作规格 `criteria[]` 是否确定为诊断和修改补丁的核心关联方式。
5. 第三方图片授权按每个任务、每个供应商还是每次请求记录。
6. 图片格式、单文件大小、单轮图片数量和任务总存储限制。
7. Skills 完整性校验失败后是否允许管理员强制发布。
8. Demo 固定案例数量、案例类型、最大允许轮次和实验通过标准。
9. 首批进入展厅的图片 Skills 清单。
10. 重大规格变化的精确判断规则是否完全由用户决定，还是由系统提示后用户确认。

## 18. 当前开发顺序建议

1. 确认创作规格、诊断结果和修改补丁的数据结构。
2. 实现任务、轮次、分支和本地存储。
3. 使用模拟模型跑通完整诊断迭代闭环。
4. 接入一个外部多模态 API。
5. 完成诊断 Web 界面。
6. 完成本地 Skills 展厅、手动发布和校验。
7. 建立固定案例并完成对比实验。
8. 在核心流程稳定后增加 Codex Skill、MCP、协作和多供应商能力。
