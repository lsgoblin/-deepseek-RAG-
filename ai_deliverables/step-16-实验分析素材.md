# Step 16 实验分析素材

## 选题说明

本项目没有停留在通用问答演示，而是把 RAG 主链路落地到了“AI 生图提示词优化”这一更具体的应用场景。这个场景对提示词的结构化程度、风格控制、细节约束和可复用性要求更高，适合展示 RAG 在创作辅助中的价值。

## RAG 的作用

RAG 让系统不是只靠模型“凭经验改写”，而是先从本地知识库中检索已有提示词模式、构图元素和风格组合，再把这些可追溯参考注入生成阶段。这样做有两个直接收益：

- 输出更稳定，不容易偏离用户原始主题
- 每次优化都能回溯到具体来源片段，便于课程实验展示

## 三种模式的差异

`LLM-only` 的优点是响应简单直接，但缺点是容易泛化成“看起来合理”的常见描述，缺少和本项目知识库相关的结构化经验。

`Retrieval-only` 能清楚展示系统检索到了哪些参考材料，优势是证据透明、可追溯性强，但它本身不产生最终可直接使用的优化提示词。

`RAG` 把前两者结合起来，既保留检索依据，又能输出完整结果，最适合课程报告中展示“先检索、后生成”的完整链路。

## 优化前后差异分析

在人物类样例中，优化前提示词只有主体和大致场景；优化后通常会补足镜头、服饰材质、环境细节和光效信息。

在场景类样例中，优化前提示词往往只描述一个静态地点；优化后会进一步引入层次、气氛、时间感和空间纵深。

在产品海报类样例中，优化前提示词通常过于宽泛；优化后会加入商业摄影常见的布光、背景、品牌调性和构图焦点。

## 为什么 RAG 优于直接生成

- RAG 可以利用知识库里的既有表达模式，减少模型自由发挥带来的漂移
- RAG 输出能附带来源片段，更适合课程答辩和报告写作
- 当输入比较简短时，RAG 更容易补足结构化维度

## 当前局限

- 检索质量仍依赖知识库内容覆盖面
- 对比实验目前以命令行和 Markdown 结果为主，未单独做成第二个 Web 页面
- 如果 API Key 缺失，系统只能验证检索链路，无法完整验证生成链路
